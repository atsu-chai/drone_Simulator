# 合格実績につなげる要件定義・最低品質基準 v2

作成日：2026-10-21／状態：提案版（対象区分・協力者・日程は要確定）

## 1. 目的と確定事項

開発者本人は合格済み。開発者以外の受験者が、本サービスで練習して指定試験機関の直接受験に合格する実績を作る。
最初の製品目標は、少人数の受験者について「練習→弱点改善→実機確認→受験結果」を追跡できる訓練版を完成させること。
初期対象は二等・回転翼航空機（マルチローター）・基本（昼間、目視内、25kg未満）を提案する。対象区分は最終確認が必要。
学科・身体検査・申請などの進捗は記録するが、初期版で資格取得全体の教材を作ることは目標に含めない。

## 2. 現状評価

ローカルの README、仕様書、HTML、JavaScript を静的に調査した。ブラウザでの完走、実コントローラー、実機との比較、利用者の合格実績は今回未検証。完成率の数値化は行わない。

| 領域 | コード上の現状 | 合格支援として不足する点 |
|---|---|---|
| 3D・機体物理 | Three.js、モデル、120Hz固定刻み、位置保持切替 | 実機との応答比較・監修記録がない。リアルさの検証が必要 |
| 科目進行 | 点検→スクエア→8の字→異常事態→点検→結果 | 単科目反復、段階教材、机上・事故対応の設問がない |
| 経路評価 | 通過点の距離と高度で進行 | 線分・円弧全体を飛んだことの検証が不足。通過点だけを狙う練習になる恐れ |
| 区画判定 | x=-10.5〜10.5、z=-2〜18の外周で反射・回数加算 | 科目別の減点・不合格区画に対応していない。描画した境界と採点を一致させる必要 |
| 採点 | 高度・機首の全体RMS、独自配点、70点で合否表示 | 発生事象と公式項目の対応がない。全体平均で局所的な重大ミスを見落とす恐れ |
| 点検 | 前6項目・後3項目を順番にクリック | 状況判断・異常発見・申告・記録の練習が不足。独自の順序罰を公式減点と混同しない |
| 操作 | Gamepad検出、複数プリセット表示 | 現状のプリセットは実質同じ軸割当。校正と実機確認が必要。開発者操作は初期ON |
| 中断 | 切断イベントで接続表示を更新 | 切断・フォーカス喪失時の停止方針がない。壁時計と物理時間のずれの検証も必要 |
| 視点・案内 | 操縦者位置から機体を追うカメラ、目標リング | 試験モードでも補助表示の統制が不足。画角・目の高さ・科目ごとの位置を要照合 |
| 記録 | 1Hz座標等をJSON出力 | 履歴、入力、採点イベント、版情報、実際の受験結果を結び付けられない |
| 表示 | 風速2.6m/sを固定表示・ログ出力 | 風を物理に適用していない。無風と環境参考値の区別が必要 |

根拠箇所：app.js の checklistItems / readInput / updatePhysics / updateMission / finishExam / recordTelemetry / loop、index.html。
結論：一連の体験を示す試作の基盤はあるが、学習効果・採点妥当性を保証できる段階ではない。まず評価と反復学習を整える。

## 3. 制度資料と適合管理

2026-10-21に次の一次資料を確認。公開前と検証開始前に改訂を再確認する。

- [国土交通省・技能証明資料一覧](https://www.mlit.go.jp/koku/license.html)：2026年6月5日適用資料への入口。
- [実地試験実施基準](https://www.mlit.go.jp/koku/content/001971373.pdf)
- [二等マルチローター実地試験実施細則](https://www.mlit.go.jp/koku/content/001971375.pdf)：PDF p.2〜10の採点、p.11以降の基本区分を参照。
- [指定試験機関の試験案内](https://ua-remote-pilot-exam.com/)：受験手順・当日の運用は検証開始前に別途確認する（今回、詳細未調査）。

細則には机上・前後点検・実技・事故対応が含まれる。区画判定、初回逸脱時の復帰猶予、科目ごとの採点には条件があるため、単なる外周接触回数に置き換えない。
公式の判断を自動化できない事項は、未評価と明示し指導者確認へ回す。独自の物理閾値を公式値として扱わない。

実装前に対応表を作る。各行には「要件ID／公式文書・ページ・項目／対象科目／条件と例外／画面・判定処理／確認シナリオ／監修者・確認日」を持たせる。
コース図はPDFの図を目視確認して座標化し、既存仕様書の数値をそのまま正としない。

## 4. 最小実装範囲と受入条件

以下の数値は製品の提案基準であり、公式試験基準ではない。

| ID | 必須要件 | 完了を判断する条件 |
|---|---|---|
| R01 | 対象試験・対応範囲・資料版を表示 | 初回と結果画面で対象区分、未評価項目、公式認定ではないことが分かる |
| R02 | 対応環境を限定 | 最初はPC・指定ブラウザ・実機確認済みコントローラー1機種。OS・ブラウザ版・接続方式を明記 |
| R03 | 操作確認と校正 | 全軸の向き・中立・最大入力を開始前に確認でき、設定保存可。開発者操作は通常利用で初期OFF |
| R04 | 中断処理 | 切断・タブ離脱時は進行と採点を停止。入力を解除。復帰時に再校正確認し、模擬試験は中断扱いで再開可否を明示 |
| R05 | 基礎→単科目→通しの学習導線 | 離着陸・ホバリング・向き別操作から各科目へ進める。苦手科目を1操作で再練習できる |
| R06 | 3科目の経路・進行 | コース、機首、ホバリング、着陸、時間を対応表と照合。逆走・ショートカット・未完了で正常完了しない |
| R07 | 連続的な区画判定 | 描画と評価を同じコース定義から生成。警告・復帰・再侵入・不合格をイベント記録。フレーム単位の重複減点を防ぐ |
| R08 | 根拠を説明できる模擬評価 | いつ・どこで・何の項目を評価したかを表示。公式準拠部分と独自練習指標を分ける。未評価がある場合、総合合格相当と断定しない |
| R09 | 点検・机上・事故対応 | 前後点検の判断・申告・記録、飛行計画の設問、事故対応の設問と解説を収録。クリック順の暗記だけで完了しない |
| R10 | 練習と模擬試験の区別 | 練習は経路・修正案を表示。模擬は独自の目標誘導・途中点数を隠す。必要な試験員の指示・警告は残す |
| R11 | 結果から次の練習へ | 科目別のミス一覧、位置・時刻、優先改善点を最大3件、再練習導線。直近5回を比較できる |
| R12 | 記録の保存・出力 | 匿名ID、実施日時、ソフト・採点・コース・物理版、校正、環境、中断、イベントを保存。再読込後も閲覧・出力可能 |
| R13 | 指導者が確認できる振り返り | 航跡とミスの時刻を対応させて確認可。1Hz表示ログとは別に判定時点の位置・入力・状態を保存。高頻度ログの必要性は検証で決める |
| R14 | 操縦・視認性の監修 | 合格済みの開発者と、独立した指導経験者1名以上が実機と比較し、誤学習につながる指摘を解消 |
| R15 | 初回利用の成立 | 初見の対象者3名全員が、口頭補助なしに接続確認→最初の練習→結果確認を完了 |

合成音声は飛行中の画面注視を減らすため、最低限の試験指示から実装する。字幕・音量を設定可能にし、発話失敗時も進行不能にしない。
点検教材は安全上必要な順序と、複数順序が許される確認を監修して区別する。

## 5. 品質の最低線

### 検証参加者に渡せる条件

- R01〜R15の確認記録がそろい、誤った合否・進行停止・入力逆転・記録消失の既知不具合がない。
- 対応環境で通し練習を10回完走し、結果・出力・再起動後の履歴を確認。正常系だけでなく、中断も確認する。
- 区画内外、境界上、初回復帰、再侵入、不合格侵入、制限時間直前直後、未完了、着陸失敗の判定事例を用意する。同じ記録と設定なら同じ結果になる。
- 30fps・60fps相当の表示で同一入力列を比較し、科目進行と評価イベントが一致する。位置差の許容値は物理監修時に決めて固定する。
- 指定した基準PCで通常飛行30fps以上を暫定下限にし、フレーム時間と入力遅延を測定する。操作に支障があれば描画品質を下げる。
- 実機比較では、入力方向、微小入力、停止距離、旋回、位置保持ON/OFF、降下・接地、距離による見え方を記録。実機型式・設定を残す。
- 無風条件では無風と表示。物理に反映していない風やセンサーを実測値のように表示しない。

### 販売を判断できる条件

上記に加え、下記の追跡検証を実施し、実機でも改善が見られること、継続を妨げる問題が解消したことを確認する。
価格10,000円は旧仕様の仮説として保留。購入意思と支援コストを確認して決める。
合格者が出ても、シミュレーター単独の効果や合格保証を意味しない。

## 6. 合格実績を作る検証計画

最初の5名を提案する。開発者は参加者数に含めない。募集・日程調整・連絡は別途行う。

1. 直接受験予定者を選ぶ。経験、実機練習歴、学科の状況、受験予定時期を記録する。
2. 利用前に共通課題をシミュレーターと指導者管理下の実機で評価する。実機を使える協力先の確保を先行条件にする。
3. 仮の練習量は1回20分・週3回・4週間。得意不得意に応じて変更し、実際の利用量を記録する。
4. 毎週、課題完了・区画逸脱・高度維持・着陸・点検理解を確認。重大な誤学習があれば検証を止めて修正する。
5. 受験前に同じ実機課題を再評価する。可能なら指導者には利用量・模擬点数を伏せて評価してもらう。
6. 指定試験機関の実地結果を追跡。実地合格と技能証明取得を別の状態で記録する。不合格・未受験・離脱も残す。
7. 本人の同意を得て合格日・受験回数等を確認。公開利用の同意は検証参加の同意と分ける。

記録項目：匿名ID、経験、利用開始・終了、練習回数・分数、前後評価、実機練習時間、外部講習・指導、受験日・回数、結果、未受験理由、証拠確認日、掲載同意。
初期保存はローカル履歴＋運営管理の表でよい。クラウド会員システムは必須にしない。氏名や証明書画像を飛行ログへ入れない。

提案する判断基準：5名全員の状況を追跡し、4名以上が予定練習の80%以上を実施。実機の重大ミスが増えた参加者は原因を個別検討し、3名以上で事前に定めた弱点の改善を確認する。最初の実地合格者1名で事例を作り、受験者3名以上の結果がそろってから次段階を判断する。
これは小規模な実行可能性の確認であり、有効性の統計的証明ではない。割合は必ず分母を表示する（例：参加5名、受験3名、合格2名、未受験2名）。

## 7. 実装の順番

| 段階 | 作業 | 次に進む条件 |
|---|---|---|
| A：正しさを確定 | 対象区分、公式対応表、コース図、採点イベント設計、監修者確保 | 対象と判定事例をレビュー済み |
| B：評価を修正 | コース定義共通化、連続経路・区画判定、イベント採点、誤解を招く表示の修正 | 正常・失敗・境界の確認が通る |
| C：練習を成立 | 校正、中断、単科目反復、段階教材、机上・口述、音声指示 | 初見利用と実機比較が通る |
| D：改善を追跡 | 履歴、振り返り、出力、前後比較と受験結果の運用 | 参加者に渡せる品質基準を満たす |
| E：合格を追跡 | 5名の検証、実機再評価、受験結果、課題の修正 | 販売または再検証の判断材料がそろう |

着手時には app.js を「入力・物理・コース・進行・評価・保存・表示」に分け、まず評価に必要な境界を作る。フレームワーク移行を先行目標にしない。
工期は協力者・開発稼働・受験日程の確定後に見積もる。合格までの日程とソフト開発完了日を分ける。

## 8. 初期版から外すもの

スマホ・タブレット全般、全コントローラー保証、一等・限定変更、高度な風モデル、音声認識、豪華な背景追加、オンライン対戦、課金・会員管理、AIによる高度診断。
旧仕様の広い対応環境と将来機能は候補として残し、この文書の初期範囲へ自動的に含めない。
